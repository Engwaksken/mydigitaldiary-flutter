# Personal Monitor — Flutter Mobile App Setup

This folder has the Dart source code (`lib/`) and `pubspec.yaml` hand-written and
ready to go, but it's **not** a runnable Flutter project yet — the `android/`,
`ios/`, and other native platform folders only get generated by actually running
the Flutter SDK, which isn't available in the environment these files were
written in. Here's exactly how to turn this into a real project in VS Code.

## 1. One-time prerequisites

- Install the Flutter SDK (https://docs.flutter.dev/get-started/install)
- Install the Flutter and Dart extensions in VS Code
- `flutter doctor` should show no blocking issues for the platform(s) you're
  targeting (Xcode for iOS, Android Studio's SDK/emulator for Android)

## 2. Create the real project scaffold, then drop these files in

```bash
cd wherever/you/keep/projects
flutter create personal_monitor_mobile
```

This generates `android/`, `ios/`, `web/`, `test/`, and its own starter
`lib/main.dart` and `pubspec.yaml`. Now overwrite/merge with what's here:

```bash
# From inside the folder flutter create just made:
rm -rf lib
cp -r /path/to/these/files/lib .
cp /path/to/these/files/pubspec.yaml .
```

## 3. Install dependencies

```bash
flutter pub get
```

## 3a. Required native permissions (microphone + photo library)

This update added meeting audio recording (`record` package) and a business
card photo picker (`image_picker`) — both need permission strings declared
in the native project files that only exist *after* step 2's `flutter create`
has generated them. Without these, the OS denies access outright (recording
silently fails; the photo picker either crashes or shows nothing), and there's
no way for this delivery to add them itself since they don't exist yet at the
point these files were written.

**Android** — add both lines inside `android/app/src/main/AndroidManifest.xml`'s
`<manifest>` tag, alongside (not replacing) whatever's already there:

```xml
<uses-permission android:name="android.permission.RECORD_AUDIO" />
<uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />
```

`READ_MEDIA_IMAGES` is the modern (API 33+) equivalent of storage-read
access for photo picking. If you're supporting older Android versions too,
check `image_picker`'s own README for whether `READ_EXTERNAL_STORAGE` is
still needed for your minimum SDK — that requirement has shifted across
Android and package versions, and is worth confirming against whatever's
current when you actually build this.

**iOS** — add both keys inside `ios/Runner/Info.plist`'s outermost `<dict>`:

```xml
<key>NSMicrophoneUsageDescription</key>
<string>Personal Monitor needs microphone access to record meetings.</string>
<key>NSPhotoLibraryUsageDescription</key>
<string>Personal Monitor needs photo library access to set your business card photo.</string>
```

The string values are what iOS actually shows the user in the permission
prompt — reword them if you'd like, just don't remove the keys themselves.

Test on a real device or simulator that the microphone permission prompt
actually appears the first time "Start Recording" is tapped, and that a
recording made after granting it actually produces a playable file — this
is the one part of this update that genuinely can't be verified without a
running Flutter environment, which this sandbox doesn't have.

## 4. Firebase setup (required for push notifications)

1. Create a Firebase project at https://console.firebase.google.com if you
   don't have one yet.
2. Install the FlutterFire CLI: `dart pub global activate flutterfire_cli`
3. From the project root: `flutterfire configure` — follow the prompts,
   selecting your Firebase project and both iOS + Android as platforms.
   This generates `lib/firebase_options.dart` (referenced by `main.dart`'s
   `Firebase.initializeApp()` — no code change needed, just run the command).
4. **For the Laravel backend** (not this Flutter project): Firebase Console ->
   Project Settings -> Service Accounts -> "Generate new private key". Save
   that JSON file to your Laravel app's `storage/app/firebase-service-account.json`
   and set `FIREBASE_PROJECT_ID` + `FIREBASE_CREDENTIALS_PATH` in `.env` — see
   `app/Services/FcmService.php`'s doc comment on the Laravel side for the
   exact steps.

## 5. Point the app at your Laravel API

Edit `lib/services/api_client.dart`'s `baseUrl`:

- **Android emulator** talking to a Laravel server on the SAME machine:
  `http://10.0.2.2:8000/api` (already the default) — 10.0.2.2 is the
  emulator's special alias for the host machine's localhost.
- **iOS simulator** talking to a Laravel server on the same machine:
  `http://127.0.0.1:8000/api` (iOS simulator shares the host's network
  directly, unlike Android's emulator).
- **A physical phone** (either platform): your computer's actual LAN IP,
  e.g. `http://192.168.1.50:8000/api` — find it with `ipconfig` (Windows)
  or `ifconfig`/`ip addr` (Mac/Linux). Both devices need to be on the same
  Wi-Fi network.
- **Production**: your real domain over `https://`.

## 6. Laravel-side setup (do this once, on the Laravel app itself)

```bash
composer require laravel/sanctum
```

Then:
- Copy `config/sanctum.php` from this delivery into your Laravel app's `config/`
- Copy the two new migrations (`..._create_personal_access_tokens_table.php`,
  `..._create_device_tokens_table.php`) into `database/migrations/`
- Merge `config-notes/services-php-firebase-addition.php`'s one array entry
  into your existing `config/services.php`
- Add `api: __DIR__.'/../routes/api.php'` to `bootstrap/app.php`'s
  `withRouting()` call — see the comment at the top of `routes/api.php`
- `php artisan migrate`

## 7. Run it

```bash
flutter run
```

VS Code's device picker (bottom-right status bar) lets you choose a
specific simulator/emulator/physical device before pressing F5 / Run.

## What's built

**Fully working, bespoke screens:** registration, login + OTP verification
(mirrors the web app's two-step flow exactly), logout, FCM push
registration/reception, dashboard stat cards, and three modules with their
own hand-written screens — Reminders, Meetings, and Expenses (list, create,
edit, delete, pull-to-refresh each).

**Fully working, generic engine:** every other module — Plans, Income,
Budgets, Debts, Savings Goals, Contributions, Diet, Exercise, Sleep, Health
Checkups, Projects, Tasks, Education, Network, Relationships, Spiritual
Growth, Feedback (17 in total) — goes through one shared screen,
`lib/screens/dynamic_crud_screen.dart`, driven by a config object per module
in `lib/config/module_configs.dart`. Rather than 17 near-identical ~250-line
screen files, each module is a ~15-line config entry (field names, types,
select options) transcribed directly from that module's web
`{Module}Controller.php` `$fields`/`$rules` arrays — the same relationship
`ApiCrudController` has to each `Api\{Module}Controller` on the Laravel
side, just one layer further down into the actual UI. All 20 modules are
now reachable from the dashboard's grouped module list (grouped the same
way as the web app's sidebar: Finance / Health & Wellness / Work & Projects
/ Personal Life / Productivity / Tools & Account).

**One real limitation, not a bug:** two fields — Contributions'
`savings_goal_id` and Tasks' `project_id` — are foreign keys the web app
renders as a `<select>` populated from the user's own goals/projects. The
generic engine has no per-module code to fetch and populate that options
list (that's the whole point of it being generic), so those two are plain
numeric-ID fields with a hint telling the user which ID to enter. Fixing
this properly means either a small bespoke screen for just those two
modules, or teaching ModuleConfig about "fetch options from another
endpoint" — reasonable follow-up work, not attempted here.

**Laravel side:** every one of the 20 modules now has a matching
`Api\{Module}Controller extends ApiCrudController` in
`app/Http/Controllers/Api/`, registered in `routes/api.php`. Nothing left
in "pattern to repeat" state on the API layer.

## This update — four features brought over from the web app

Added on top of everything above, matching web features that shipped after
the original 20-module build: **Business Card** (view/edit, photo upload,
QR code, share/open the public page, publish toggle), **Signatures**
(view/download saved signatures and signed documents — deliberately NOT the
full drag-and-drop multi-page signing editor, which depends on a browser's
PDF rendering and isn't a reasonable port to a native app), **Subscription**
(plans grouped by category with the same colors/badges as the web pricing
page, a checkout bottom sheet for card/mobile-money, and an invoice/receipt
list), and **Meetings recording, transcript, and AI summary** (consent
dialog, start/pause/resume/stop with a live timer via the `record` package,
timestamped transcript, AI-generated summary).

Three new packages were added to `pubspec.yaml` for this — `record`,
`image_picker`, and `path_provider` — alongside `url_launcher` and
`share_plus` from the previous round. None of these could be verified with
a real `flutter pub get` from the sandbox they were written in (no Flutter
toolchain available there); they're all widely-used, stable packages, but
run `flutter pub get` and resolve any version conflicts before trusting
this blindly — see 3a above specifically for the two that need native
permission setup to actually work.

**A cross-platform bug fixed as part of this work, not mobile-specific:**
buying a Family/Team or Organization plan never actually created an
Organization record on the Laravel side, on web OR mobile — the buyer
would pay, then find no organization to manage. Fixed in the Laravel
backend itself (all three payment-completion paths), so this is already
correct for both platforms once you deploy that fix; nothing needed here.

**Also fixed:** `ApiClient` didn't have a `patch()` method, but the
recording-status-update endpoint is a PATCH route — calling it as PUT
would have returned a 405 error the first time someone tried to pause a
recording. Fixed alongside building the recording screen.

## AI Planner — deliberately not included

The web app's AI Planner isn't part of the mobile module list. It's built
around the user's own API key (or the admin's shared fallback) and
multi-step generation flow that doesn't map onto the same list+form shape
as every other module — bringing it to mobile would need its own bespoke
screen, not a `ModuleConfig` entry. Flagging it explicitly rather than
letting it look like an oversight.

## Required Android setup for reminders while the app is closed

The mobile app now schedules reminder alarms **on the phone itself** whenever
reminders are loaded/created/updated. This means the alarm can fire while the
app is backgrounded, terminated, or showing the login screen. Local schedules
are intentionally not removed on logout.

Because `flutter_local_notifications` 16+ no longer injects all scheduling
receivers into the app automatically, merge these into your generated
`android/app/src/main/AndroidManifest.xml`.

Between the outer `<manifest>` tags (outside `<application>`):

```xml
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
```

Inside `<application> ... </application>`:

```xml
<receiver
    android:exported="false"
    android:name="com.dexterous.flutterlocalnotifications.ScheduledNotificationReceiver" />

<receiver
    android:exported="false"
    android:name="com.dexterous.flutterlocalnotifications.ScheduledNotificationBootReceiver">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED"/>
        <action android:name="android.intent.action.MY_PACKAGE_REPLACED"/>
        <action android:name="android.intent.action.QUICKBOOT_POWERON" />
        <action android:name="com.htc.intent.action.QUICKBOOT_POWERON"/>
    </intent-filter>
</receiver>
```

The app uses `AndroidScheduleMode.inexactAllowWhileIdle`, so it does **not**
need exact-alarm permission. This avoids the Android 14 exact-alarm approval
flow while still allowing reminders to fire during idle/Doze (the OS may shift
them slightly).

`flutter_local_notifications` also requires core-library desugaring on Android.
If your generated `android/app/build.gradle.kts` does not already have it,
merge:

```kotlin
android {
    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_11
        targetCompatibility = JavaVersion.VERSION_11
        isCoreLibraryDesugaringEnabled = true
    }
}

dependencies {
    coreLibraryDesugaring("com.android.tools:desugar_jdk_libs:2.1.4")
}
```

After merging the native changes, run:

```powershell
flutter clean
flutter pub get
flutter analyze
flutter run
```
